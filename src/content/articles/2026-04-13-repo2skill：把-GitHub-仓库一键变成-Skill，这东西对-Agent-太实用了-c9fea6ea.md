# repo2skill：把 GitHub 仓库一键变成 Skill，这东西对 Agent 太实用了

我最近越来越确定一件事：很多人不是不会用 Agent，而是不会把“外面的东西”接进 Agent。

你明明在 GitHub 上刷到一个不错的仓库，觉得这玩意儿对 OpenClaw、Claude Code、OpenCode 都有帮助，结果一到真正要用的时候，人就开始萎了。README 太长，代码太多，配置太杂，手工复制粘贴又像在给自己加班。最后最常见的结局不是“用起来了”，而是“先 star，回头再说”。

repo2skill 想解决的，就是这个特别现实、特别不性感的问题：**把一个仓库，直接转成 Agent 能理解、能调用、能复用的 Skill。**

这东西厉害的地方不在“概念新”，而在它够直白。不给你讲什么云里雾里的 Agent 操作系统，不要求你先搭一堆基础设施，也不逼你去配额外 API key。它给的承诺很简单：给我一个 GitHub / GitLab / Gitee 链接，或者一个本地项目路径，我帮你把它变成一个完整技能包。

---

## 这个项目是干嘛的（一句话）

repo2skill 是一个“仓库转技能转换器”，目标是把任意开源仓库或本地项目，转换成 OpenCode / Claude Code 可以直接理解和使用的完整 Skill。

说人话，它做的是：**把“看仓库学项目”这件事，变成“把仓库收成可执行技能”这件事。**

---

## 它解决了什么问题

我觉得这个项目最对的一点，是它没有把问题想得太浪漫。它直面的是几个非常俗、但每个做 Agent 的人都绕不过去的痛点。

第一，仓库太大，AI 一口吃不下。你把一个像样的 GitHub 项目直接塞给 Agent，它不是吃不完，就是吃得乱七八糟。第二，配置太复杂，很多有价值的仓库根本不止 README 一页，它后面还有安装方式、目录结构、依赖约束、文档文件、API 说明、FAQ、测试方式。这些信息散着放的时候，人都懒得整理，别说让 Agent 稳定理解。第三，手工复制粘贴真的很烦，尤其当你已经知道“这个仓库值得做成长期能力”的时候，再让你一段段摘、一次次喂，像在用铲子搬沙子。

repo2skill 的做法，是把“采集 → 分析 → 整理 → 生成 Skill”这条线包起来。它既支持远程仓库，也支持本地项目；既支持 GitHub，也支持 GitLab 和 Gitee；还能用你当前在 OpenCode / Claude Code 里已经配置好的 LLM 去做分析。这个设计特别接地气，因为它没要求你为“转换技能”这件事再多养一套系统。

---

## 核心功能亮点

### 它不只吃 GitHub，还吃 GitLab、Gitee 和本地目录
这个点很关键。很多工具一写“支持仓库”，本质上只支持 GitHub，而且还只支持最干净的那种 URL。repo2skill 这边把远程和本地都做进去了，还明确列了 GitHub、GitLab、Gitee 三个平台。

这在实际里有啥用？你不用再把“仓库来源”当成额外障碍。国内项目、私有镜像、本地代码都能进同一套转换路径。

### 智能镜像轮换 + 重试逻辑，不让 GitHub 抽风把流程直接打死
它内置了 10+ 镜像端点、自动故障转移、速率限制处理，还有指数退避。

这在实际里意味着什么？意味着它知道现实世界的网络不稳定，知道 GitHub 不是总会老老实实回你数据。一个做“仓库转 Skill”的工具，如果连拉代码这一步都很脆，那基本就废了。这个项目至少在这里是清醒的。

### 零依赖、不开新坑
README 里写得很重：无需 npm install，无需外部包，无需额外 API keys。

这点很讨喜。因为现在很多工具的套路都是：为了省 5 分钟，先让你搭半天环境。repo2skill 至少在姿态上不是这种玩意儿。它更像“给你一把现成扳手”，不是先给你发一张建厂清单。

### 生成出来的不是“摘要”，而是完整 Skill
它不是把仓库读完后给你一篇介绍文就完事，而是直接生成一个完整技能，里面会包含 YAML frontmatter、安装、使用、API、配置、FAQ、故障排除、最佳实践、资源链接这些结构。

这在实际里有啥用？说明它想要的不是“帮你理解一次”，而是“帮你变成可重复调用的能力”。这个方向就对了。一次性理解不值钱，长期复用才值钱。

### 批量转换也考虑到了
README 里明确说支持同时转换多个仓库，并行处理。

这个点对“爱囤仓库的人”特别实用。你不用一个个手搓，而是可以把那堆 star 过、但一直没消化的项目，一口气丢进去处理。

## 快速开始

### 安装（30 秒）

```bash
# 选项 1: 全局(推荐用于所有项目)
mkdir -p ~/.config/opencode/skills
cp -r repo2skill ~/.config/opencode/skills/

# 选项 2: Claude 兼容
mkdir -p ~/.claude/skills
cp -r repo2skill ~/.claude/skills/

# 选项 3: 项目特定
mkdir -p your-project/.opencode/skills
cp -r repo2skill your-project/.opencode/skills/
```

### 使用（一个命令）

```text
帮我把这个仓库转成技能:https://github.com/vercel/next.js
```

```text
帮我把当前项目转成技能

帮我把这个本地项目转成技能:./my-project
```

技能会自动：
1. 检测输入类型(远程 URL 或本地路径)
2. 获取/提取数据(从镜像或本地文件系统)
3. 使用你配置的 LLM 分析仓库
4. 生成包含 18+ 章节的完整 SKILL.md
5. 询问你想把生成的技能保存到哪里

### 批量转换示例

```text
帮我转换这几个仓库:
- https://github.com/vercel/next.js
- https://github.com/facebook/react
- https://github.com/anthropics/anthropic-sdk-typescript
```

### 可选：API Token

```bash
# GitHub token(逗号分隔用于轮换)
export GITHUB_TOKENS="ghp_xxx,ghp_yyy,ghp_zzz"

# GitLab token
export GITLAB_TOKENS="glpat_xxx,glpat_yyy"

# Gitee token
export GITEE_TOKEN="your_token"
```

## 关键用法 / 示例

这个项目最顺的一点，是它把“本地项目”和“远程仓库”放进了同一套使用范式。你可以直接说“帮我把当前项目转成技能”，也可以丢一个 GitHub 链接。对人来说这很自然，对 Agent 来说也很省脑子，因为它不用再区分两套完全不同的工作模式。

README 里给了好几个场景：热门框架、小型工具库、中文仓库、本地前端项目、批量转换多个仓库。尤其是“本地项目支持”这一块挺有感觉，因为很多真正有价值的东西根本不在 GitHub 上，而是在你电脑里那个已经跑了半年、但文档烂得像事故现场的项目目录里。repo2skill 试图把那种“只有人懂”的项目，也往 Skill 这种结构化产物上拉。

还有一个我觉得挺重要的点，是它没有把“生成 Skill”理解成“生成一个说明文档”。从它给出的结构看，它想生成的是一套可长期用的技能说明，包括安装、开发、测试、FAQ、排障、最佳实践这些。这说明作者心里想的不是“看完就算”，而是“以后真会拿来用”。

## 使用感受（不官方版）

我对这类项目有个很简单的判断标准：它是在帮你减少一次性劳动，还是在给你制造新的维护成本。repo2skill 目前看，方向是对的，因为它抓的不是“让 AI 多懂一点仓库”，而是“让仓库真正变成 Agent 的可复用能力”。

但也别上头。它再顺，也不代表所有仓库都值得转成 Skill。有些项目你看一遍 README 就够了，硬转反而是仪式感过剩。真正值钱的，是那些你明确知道“后面还会反复用”的仓库和本地项目。

还有一点要提醒：README 里虽然强调零依赖、无需额外 API keys，但它并不是“零前提”。它依赖你在 OpenCode / Claude Code 里已经有可用的 LLM，这个前提别忘了。别到时候一边说它没反应，一边自己底层模型都没配好，那就属于工具没坑你，是你先坑自己。

## 注意事项 / 坑点

第一个坑，其实不是技术坑，是选择坑。不是每个仓库都值得转 Skill。小而短、一次性看完就走的项目，硬转只会增加维护负担。

第二个坑，是平台和网络。它虽然做了镜像轮换和重试，但这不等于网络问题被神奇消灭。尤其是 GitHub 这边，抽风时还是会抽风，只不过这个项目比大多数人更认真地处理了这件事。

第三个坑，是私有仓库。README 说得很清楚，私有仓库要配对应 token。别到时拿一个 private repo 去试，然后因为 401 反过来怀疑整个工具不行。

第四个坑，是你对“生成 Skill”这件事的期待。它能帮你把仓库信息结构化、技能化，但它不是替你做判断。一个仓库值不值得收成 Skill，后面怎么维护，哪些规则该进 Skill，哪些只是一次性说明，这些仍然需要人拍板。

---

## 一句话总结

**repo2skill 真正值钱的地方，不是“让 AI 再多读一个仓库”，而是试图把“读完仓库就忘”这件事，升级成“把仓库收成可长期复用的 Skill”。**
