# new-term-radar 解读：它把新名字出现当天的提前量做成了工程

「Strata」「Seedance」这类 AI 新词有个本事：出现当天就满天飞，可关键词工具里查不到，等 Google Trends 有曲线已经是几天到几周之后。做 AI 工具站、写 Newsletter、开导航站的人，靠的就是这几天差价——**别人还没收录这个词的时候，页面已经占好位了**。问题在于怎么系统性地「提前」，而不是天天刷 X 碰运气。

new-term-radar（新词雷达）就是冲这个来的。它每天固定产出一份报告，列出 AI 圈刚开始冒头的名字：新模型、新产品、新工具、新仓库。v0.5.0，Python 3.10+，零第三方依赖（标准库就够跑），MIT，PyPI 包名 `new-term-radar`。首日 700+ 星，三天出头破 1000，现在约 1.5k，已挂官方 MCP Registry、Cursor Directory、LobeHub、Tessl、ClawHub、skills.sh。

它的核心命题一句话：**关键词工具读的是结果，它读的是结果出现之前的信号**。README 把一个新名字的完整生命周期列成五步：① 实验室或大号在 X 上先说话；② GitHub 上某个仓库自己涨起来；③ 导航站和竞品加页面、新站开始有排名；④ 你自己的站第一次因为这个词有搜索曝光；⑤ Google Trends 出现曲线。关键词工具读第 5 步，雷达每天读第 1 到 4 步，第 5 步只用来复盘自己准不准。

仓库实际有什么，对应到源码目录是这样的分层：

| 层 | 源码目录 | 对应职责 |
|---|---|---|
| 命令入口 | `radar/__main__.py` | `daily` / `sources` / `pains` / `history` 子命令、`--skip` 开关 |
| 8 路信号 | `radar/social.py` `breakout.py` `sitemaps.py` `new_sites.py` `sellers.py` `revenue.py` `asks.py` `gsc.py` | X / GitHub 爆发 / sitemap / 新站 / 新卖家 / 收入 / Reddit 求助 / Search Console |
| 名字判断 | `radar/judge.py` | 小模型给每个词打分：具体东西的名字，还是普通词 |
| 新词表 | `radar/usecases.py` | 名字背后的通用搜索词：取证→提词→筛选→搜索量→Trends→首页竞争 |
| 复盘闭环 | `radar/review.py` | 每条线索 14 天后去 Google Trends 核对，输出命中率 + 提前天数 |
| MCP / Skill | `radar/mcp_server.py`、`skills/` | 3 个 Agent Skill（new-term-radar / ai-listening / seo-new-keywords-research） |

## 它先想清楚了一件事：名字和它背后的需求是两回事

「SynthID Detector」和「ai image detector」都来自同一个新产品，却是两种完全不同的词。前者是这个具体东西的名字，寿命短，而且是 Google 的；后者是大家拿它做的事，会一直有人搜，而且不属于任何人。README 对这两种词的处置写得很清楚：**名字读当天，通用词记进线索库，14 天后一起复盘**。

这是整个设计里最有识别度的一条分界。名字是品牌，通用词是无主的需求。做 SEO 的人天然只盯着名字抢首发，但名字本身吃不了多久流量——真正长期被人搜的是它背后的那个「做法」。雷达把两种词塞进同一张表，每行带类型、来自哪个名字、估算日搜、Trends 走势、首页竞争和决策，一天之内把「这个东西叫什么」和「大家拿它搜什么」一起给出来。

名字和普通词的区分，靠一个专属判断。`radar/judge.py` 里给模型的任务写得很细：对每个词打 0 到 1 分，判断它是某个具体产品、模型、工具、仓库的名字，还是普通词、泛类、功能描述或句子残片。0.5 分叫「老名字」——google、claude 这类成名已久的东西照给分，只是不高。报告里专有名词排前面，普通词排在后面。最关键的工程取舍在 docstring 里：**判断器只给报告排序，从不阻挡报告**——没有 key 或调用失败时，词照样全列出来，只是不分先后。一层判名字的分类器，永远不成为整条流程的断点。

## 核心机制：一道「搜索量的提前量」，两套判断

技术解读的价值在机制，挑三个和工程最相干的讲。

### 1. 提前量靠 8 路信号，不靠关键词数据

信号表是分层的，越靠前越便宜、越接近"名字第一次被说出"的时刻：

| 信号 | 抓什么 | 需要 | 花费 |
|---|---|---|---|
| ① X | 你关注的账号里 60 天内第一次出现的名字 | AIsa key | 每账号每次 $0.003 |
| ① Hugging Face | 新进热门榜前 50 的模型和 Space | 无 | 免费 |
| ② GitHub 爆发 | 创建 <14 天、日均 +200 星或比昨天 +400 星的仓库 | 无 | 免费 |
| ③ 竞品 sitemap | 新网址共用、旧网址里少见的词 | 你列 sitemap | 免费 |
| ③ 新站 | 90 天内注册且首次被收录、≥20 个排名词的域名 | AIsa key | 每查询 ~$0.13，每周 |
| ⑦ 求助 | Reddit 上「要什么」的 12 种问法 | AIsa key | 每周 ~$0.12 |
| ⑧ 新卖家 | 刚挂第一条收款链接的站 | AIsa key | 每周 ~$0.40 |
| ⑥ 收入 | TrustMRR 核验过的增长产品 | TrustMRR key | 免费，每周 |
| ④ Search Console | 你站第一次获得曝光的查询 | 你自己的 Google 授权 | 免费 |
| ⑤ 复盘 | 每条线索 14 天后核对 | AIsa key | 每写法 $0.0012 |

（价格是 2026 年 10 月 AIsa 实际收费。示例配置：35 个 X 账号、每天读三次、新词表每天 5 个名字，一个月约 $15——X 约 $10，新词表约 $5。成本是头等设计输入，不是事后记账。）

这套信号设计的原点，是 REPO 里写的一个真实案例：`Niko1221/Strata` 创建于 2026-09-24，九天后 7,700 星；9 月 26 日起就有人在搜「niko strata」，而当时没有第二个仓库用这个名字，关键词工具里也查不到。**一个仓库每天涨 800 星，本身就是全部信号，而且是公开的。** GitHub 爆发这一路（`radar/breakout.py`）读的正是这个：命中一个仓库后，附带生成大家实际会搜的写法（「niko strata」）。

### 2. 名字读两次：公告那天读不出用法

发布当天的帖子全是公告，还没有人用。所以 `radar/usecases.py` 把每个名字读两遍：出现当天一次，三天后再一次（`recheck_days` 默认 3）。第一次主要看它是什么，第二次看用法有没有长出来。通用词也走同一套，14 天后和名字一起复盘。

这背后有一条较早跑 8 个名字得出的预期，README 写得直给：**名字涨了，通用词在五天内大多没涨**。PhotoCraft、Claude Haiku 5.5、SynthID Detector 的搜索都明显上升，背后的通用词里只有一个动了——PhotoCraft 出现后，「photoshop alternative」在美国连续五天比之前高出约 80%。全球日数据几乎读不出来（2、1、1、2、4、2 这种数），配了 GoAnyAPI 后改读美国单日数据才看得清，于是「photoshop alternative」显示为 `还在涨 (US)`。**全球数据显示「没动」，不能证明这个词真的没动。** 这是对数据来源粒度的一次清醒校准。

### 3. 六步新词表：从名字到「首页还有没有位置」

`radar/usecases.py` 是产出的核心，把当天每个新名字走完六步：

1. **取证**：搜提到这个名字的高赞帖；是仓库就再读 README。
2. **提词**：模型针对每种用法写出普通人会搜的关键词，附原话作依据。
3. **筛选**：再调一次模型，给每个写法打「这个名字能不能回答这个搜索」的分。Claude Haiku 5.5 提出的 6 个全被筛掉（「ai coding assistant」「github copilot alternative」），SynthID Detector 的 5 个全部保留。
4. **搜索量**：Google Ads 月搜索量，低于 `min_volume` 的丢掉——大部分都被丢掉。
5. **Trends 两次**：单独查曲线形状，和基准词 `gpts` 一起查规模。
6. **首页竞争**：只查会采取行动的行（≤8），Google 第一页、每个站的评分、关键词难度。`能进` = 前十有 ≥3 个评分 <30 的站，或难度 <20；`挤满` = 一个弱站都没有、难度 ≥40；其余 `一般`。`挤满` 的「优先」会降成「观察 ↓」——还在涨，但首页被强站占满。

最终决策三档：**优先** = 近 30 天涨过、还在高位、估算日搜够；**观察** = 涨了但规模小 / 还太早 / 需求稳定但没动；**跳过** = 已回落 / 没动且规模小。一次真实运行（2026-10-12）的节选长这样：

```
| 关键词 | 类型 | 来自 | 新词 | 估算日搜 | 决策 |
| **photocraft** 🖼 | 名字 | — | 是 | 12747 | 优先 |
| **claude haiku 5.5** | 名字 | — | 是 | 1863 | 优先 |
| **ai image detector** 🖼 | 通用词 | synthid detector | 否 | 2537 | 观察 |
| **photoshop alternative** ⚠ | 通用词 | photocraft | 否 | 244 | 跳过 |
```

🎬🎙🖼 标记它产出什么，按「视频 > 语音 > 图片 > 文字」的付费意愿排序。⚠ 表示借了别人的品牌名（如「photoshop alternative」）——要不要用别人的品牌由你判断。⚡ = 有 1,000 赞以上的帖子在手把手教手动流程，还没人做成一键工具（在 6 个已知名字上格式全对，⚡ 只触发过一次）。

## 复盘：把"准不准"做成一条验证闭环

这是整个仓库里最适合工程视角看的部分。「It tells you which signals to trust」这句话，直接写在 `radar/review.py` 的 docstring 里，接着原话是 **「This is verification, not discovery」**——复盘不是来找新机会的，是来判断哪些信号该信。

每条线索 14 天后去 Google Trends 核对一次：`hit`（起来了，附带提前几天）/ `miss` / `no_data`，按信号来源统计命中率和提前天数。真实报告节选：

```
### ⑤ 复盘(14 天前报出的词,在 Google Trends 里起没起来)
| 词 | 首次报出 | 结论 | 提前天数 |
| strata | 2026-09-25 | hit | 3 |
```

关键技术点是把「涨」判得干净：`rose()` 不是看绝对数字，而是看线索出现之后（`first_seen` 之后）的峰值有没有超过它自己的基线——`first_seen` 之前 30 天的均值。`strata` 这个词早就存在（"strata" 有地层、分层的意思），基线本来就高，单独看不会涨；而「niko1221 strata」从 0 涨到有值，一下就判出来了。**一个带旧义的老词，天然有高基线，不靠和别人的词比，靠自己和过去比。**

这个闭环还带出几条对数据可信度的诚实，README 全写出来了：

- **Google Trends 最后两天没结算。** 互不相关的词会在这两天依次返回 0 和 100，看起来像个尖峰——第一遍就被这个骗了。现在代码里所有读 Trends 的地方都丢掉这两天（`review.py` 里的 `UNSETTLED_DAYS = 2`），上涨必须持续两天才算数。
- **Google Ads 的搜索量滞后约两个月。** 月搜只有几百的词，Trends 基本读不出可靠数。
- **新链接不等于新卖家。** 最初的版本把最新的收款链接当成新卖家；按「这个站第一次链到这个平台的日期」核对后，2026-10-14 的 2,000 条最新 Stripe 链接里有三分之二是老卖家（有个站把同一张 Stripe 链接挂在每个水井许可证页上），当天名单上的 60 个 Stripe 卖家只有 17 个是真的刚开始。现在按首次链接日期判断新卖家。

## 降级：源头挂了，表变薄，但流程不崩

雷达对"某个数据源没配或挂了"给出了系统性的处理：**表照常产出，但会变薄，并且写明缺了哪一块**。

| 情况 | 表里少了什么 | 表下面的提示 |
|---|---|---|
| 没配 `GOANYAPI_API_KEY`（默认） | 没有 🔎 相关查询、没有长尾、没有单国走势 | 「相关查询未开启：…」 |
| 某个名字的 AIsa 推文搜索失败 | 推文证据，退化成只用 README | 「推文搜索失败，这次只用了 README…」 |
| 当天没有名字得分 0.8 以上的「东西」类线索 | 整张表 | 「今天没有要读的名字…」 |
| AIsa 的搜索量或 Trends 失败 | 整张表，这两项没有替代来源 | 报错 |

README 对这时候的判断讲得很硬：**「表变薄不等于今天没动静。下结论说『什么都没涨』之前，先看表下面这几行。」** 把「信号缺失」和「信号确实没有」清楚地分成两件事——这正是检测系统最容易被误读、也让降级显式化的一步。

## 怎么落 + 前提与限制

上手一条命令链：`git clone` → `cp config.example.json config.json`（配 X 账号、sitemap、主题；`"lang":"zh"` 出中文报告）→ `export AISA_API_KEY=...` → `python -m radar daily --out report.md`。第一次跑只是建立快照（昨天的 X 词表、星数、sitemap 还没数据，只报 GitHub 爆发），从第二次起每个信号才报告变化。`python -m radar sources` 每几小时跑一次 X+HF；`daily --skip x,hf` 每天跑其余。

说限制。**所有付费部分走一个必需 key**：AIsa（X、Google Trends、域名数据背后的 DataForSEO、判名字的模型），一个 key 按次付费，不用分别订阅 X API 和 DataForSEO。可选 `GOANYAPI_API_KEY` 加相关查询和单国走势，每天约 $0.07。付费用更真——它诚实设了一档：完全没有 AIsa key 时，免费信号（HF / GitHub / sitemap / Search Console）照样跑，只是报告里所有词不分先后（没有模型判名字）。TrustMRR 的收入数据**禁止转载、禁止拿它做公开 SEO 页，只供自己研究**（README 明说）。`pains` 命令读不到的：App Store / Google Play / Trustpilot（接口限制）、There's An AI For That（前面有 Cloudflare 挑战，绕过就是违规，雷达不做）、Facebook 小组（Groups API 已关闭）。

这套东西把「抢新词首发」从手工刷 X 的玄学，变成了「名字当天抓、通用词随后跟、14 天复盘算命中率」的工程闭环。它的稀缺性不在某一个算法多强，而在**把「提前几天」这件本来靠运气的事，拆成可排程、可计费、可自评的流程**——每次命中都记下提前天数，每次误报都归咎到某一路信号。对做内容的人和做测试的人，这份「用效果数据给信号源打绩效」的纪律，是同一个追求。
