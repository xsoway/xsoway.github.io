# 一个 base_url 调五十家：Agent2API 把客户端登录态做成网关

一个人的电脑上，常常同时装着四五个 AI 客户端：Claude Code 一份配置、Codex 一份、Cherry Studio 一份、Cline 一份。每套都有自己的 base_url、key 和模型名，额度散在各家 App 里，今天这家签到送三亿 token，明天那家送一百次请求。想用的时候，先在四个窗口之间找"这笔额度现在在哪"。

[Agent2API](https://github.com/aimod-cc/Agent2API) 换了个放法：在本机起一个网关，默认监听 3065，把各家客户端的登录态转成 OpenAI 与 Anthropic 兼容接口，所有工具都指向同一个 base_url。它管两件事——模型接口的收口，和本机 Agent 客户端配置的接管。

仓库当前 2.6k star、723 fork、459 次提交、137 个 issue，许可 AGPL-3.0。桌面端用 Rust 与 Tauri 2 编译，另有服务端包和 Docker 镜像，运行时不依赖 Node。项目 About 里写的规模是"一个 base_url 调用 50+ 家模型额度"。

## 两半各自管什么

**模型接口那一半。** 对外提供 OpenAI 的 Chat、Responses、Images 和 Anthropic 的 Messages 协议，还给一份统一的模型列表。往里，是四类配置：模型映射（客户端要的名字换成某个提供商的真实模型）、账号选路（优先级、负载均衡、会话粘性、失败切换）、网关 Key（可分权）、请求报表（请求量、成功率、Token 消耗、缓存命中率、365 天热力图）。后台还有几件例行维护：刷新模型目录、维护凭证、检查更新，以及按各家自己的时间窗口执行每日签到（Qoder 10:01、ZCode 19:01，其余跟随条目时刻），另有一轮补签只处理当天没签上的账号。

**客户端配置那一半。** 本机装了几个 Agent 客户端，就有几套连接配置。这一半负责把它们收进一个界面：导入现有配置、预览即将写入的内容、在网关和自定义服务之间切换。改配置这件事不必逐个打开客户端的设置文件。

两半之间靠账号连接。账号怎么来，README 和安装文档给的方式有四种：网页登录、手机验证码、粘贴凭证、导入本机登录态。最后一种读的是客户端已经存下的登录信息，其中 AutoClaw 与智谱清言走 Windows 的 DPAPI 密文，只在 Windows 可用；小浣熊、CatPaw、Cline 读 `HOME` 下的明文文件，三个平台都能用。

还有一层插件：额外的提供商实现单独安装和更新，不随主程序打包；自定义提供商不需要插件。

## 一个请求进来以后

1. 客户端把请求发到 `http://127.0.0.1:3065/v1/chat/completions`，带上网关 Key。
2. 网关校验 Key。没建 Key 之前，`/v1/*` 一律拒绝——这是 fail-closed，安装文档特意写明它是刻意的。
3. 模型映射把客户端写的模型名换成某家提供商的真实模型。
4. 选账号：按优先级和负载均衡挑一个，会话粘性让同一段对话尽量落在同一个账号上（缓存命中率靠它），调用失败就切下一个。
5. 用这个账号的登录态向上游客户端接口发起请求；需要换出口时走代理池。
6. 结果按统一格式回给客户端，同时把请求量、成功率、Token 与缓存命中记进报表。

会话粘性这一条决定了不少实际体验。同一个账号连着问，上游的 prompt 缓存能命中，账单和延迟都低；每轮换账号，那段缓存多半用不上，钱花得更多、答得更慢。

## 装哪种形态

| 形态 | 产物 | 界面 |
|---|---|---|
| 桌面端（Windows / macOS / Linux） | `_x64-setup.exe`、`_universal.dmg`、`_amd64.deb`、`_amd64.AppImage` | 应用窗口，托盘常驻 |
| 服务端（Windows Server / Linux，无图形界面） | `agent2api-server-windows-amd64.zip`、`agent2api-server-linux-<arch>.tar.gz` | 浏览器面板 |
| Docker | `aimodcc/agent2api:latest`（amd64 / arm64） | 浏览器面板 |

选择规则写在安装文档里：自己有桌面、要托盘和本机登录态导入，装桌面端；服务器上没有图形界面，装服务端包；已经在用 Docker，拉镜像。桌面端需要图形界面，装不到无 GUI 的服务器上；服务端包不链接 WebView 和 GTK，一个可执行文件加一个 `ui/` 目录就能跑。

Docker 一行：

```bash
docker run -d --name agent2api --restart unless-stopped \
  -p 3065:3065 -v ./data:/data aimodcc/agent2api:latest
```

SQLite 库、配置、日志都落在 `./data` 一个卷里。

## 接通要走的四步

1. 装上并启动，打开 `http://127.0.0.1:3065/`（服务端与 Docker 换成主机 IP），首次进入会引导注册管理员。
2. 在「账号」页添加账号：选提供商，按弹窗提示登录或填凭证。
3. 在「网关 Key」页建一把 Key。服务端和 Docker 形态建 Key 之前转发接口是拒绝服务的。
4. 客户端 `base_url` 填 `http://127.0.0.1:3065/v1`，`api_key` 填那把 Key。桌面端在本机没启用鉴权时 `api_key` 随便填也行，但建 Key 更省事。

自测两条命令：

```bash
curl http://127.0.0.1:3065/health
curl http://127.0.0.1:3065/v1/models
```

`/v1/models` 返回的名单里有哪家，就能用哪家的名字。Python 侧和普通 OpenAI 客户端写法一致，`model` 填名单里的一个。

手机端有 `/m` 页面，可以添加到主屏幕当 PWA；Release 里还有 Android 的 `.apk` 和未签名的 iOS `.ipa`。手机端能看报表、账号状态、余额、请求日志，能启停账号与模型、一键签到、复制 Key；加账号、改凭证、改模型映射、改路由和超时这些还要回桌面端做。

## 默认是关着的

下面几个默认值决定了这台网关是"只在本机用"还是"开在网上了"，部署前先看一眼。

- **未配 Key 拒绝转发**（fail-closed）。服务端形态默认绑 `0.0.0.0`，文档给的理由是：没配 Key 就把上游额度对全网开放不可接受。`AGENT2API_ALLOW_NO_KEY=1` 能关掉这道闸，文档限定它只用于纯内网。
- **桌面端默认只听 `127.0.0.1`**。开「局域网访问」会先要求注册管理员，并自动补一把默认 Key；再开「同时开放网页管理面板」才会托管 `ui/`，浏览器和 PWA 形态依赖这个开关。
- **面板登录有人机验证**，`AGENT2API_CAPTCHA_ENABLED` 默认 `1`。
- **管理面可以分端口**：`AGENT2API_PANEL_PORT` 一开，界面和 `/api/*` 单独监听，公网只映射主端口，管理面留在内网。
- **网关默认不应答 CORS**。自建 Web UI 直连会被预检挡住，要么在设置页打开「网关跨域访问」（来源 `*`，此时任何网页都能借这台网关打上游），要么让页面与网关同源。

## 什么情况下别开

**这是给自己用的工具。** 账号是自己的，机器是自己的，把散落的免费额度收进一个接口，桌面端装完半小时能跑通。

**要分享出去，就多了一层账。** 把网关开到 `0.0.0.0`、把 Key 发给同事或朋友、或者拿它对外提供接口，等于把上游账号和额度一起交出去。项目 README 的「使用声明」只写了两段：账号凭证在本地数据库加密保存，但导出文件、备份和密钥文件仍可能含敏感数据；项目按现状提供，不保证可用性、稳定性、安全性或特定用途适用性。对各平台服务条款的相容性，文档没有给出说明，这部分得自己判断。

**客户端专属的活动额度不一定能当 API 用。** 有一篇介绍这个项目的文章提到过，某些平台每天的大额赠送明确要求在它自己的客户端内使用，不能直接折算成可被网关调用的额度。这类活动规则以各家当次公告为准，网关能做的只是把已经能调用的接口转成统一格式。

**要固定版本的人，别开容器内更新。** 面板的「下载并更新」会替换可执行文件，重启后 `docker inspect` 显示的仍是旧 tag，执行一次 `docker compose pull && up -d` 会回到镜像里的版本。文档把这条代价写在明处。

**macOS 与 iOS 都会拦一次。** dmg 里的应用没做 Apple 签名与公证（需要付费开发者账号），首次启动要去「隐私与安全性」手动放行；iOS 的 ipa 未签名，得用自己的 Apple ID 重签，免费账号七天一签。

**AGPL-3.0 带着网络条款。** 改了以后通过网络向用户提供服务，要向这些用户提供对应源码。

## 几个具体的工程取舍

Windows 服务的工作目录是 `C:\Windows\system32`，不是 exe 所在目录。安装脚本把数据目录显式写进服务注册表的 `AGENT2API_PROXY_HOME`，不写的话数据会落到 LocalSystem 的 systemprofile 下，几乎找不到——文档把这类坑和脚本的处理方式一起写了出来。

同一份 `agent2api-server-linux-<arch>.tar.gz` 同时服务两种用途：容器里当更新载荷解包替换，裸机上 `install.sh` 装成 systemd 服务。容器更新只按名取包内两个条目（`selfupdate::extract_bundle`），其余读完即丢。

镜像里内置 jemalloc，长时间多账号并发转发时比系统分配器少产生内存碎片。小内存机器建议给容器设上限，超限被内核杀掉再被 `restart: unless-stopped` 拉起，表现为重启一次，而不是把宿主机拖垮；1g 只是起点。

systemd 侧配了 `Restart=always` 和 SIGTERM 优雅停机，等在途请求跑完再退出，SSE 长连接不会被打断。

文档的维护方式也能看出作者的意图：安装细节只放在 `docs/install.md`，另有五份译文一一对应；各语言 README 只留速查表和指向安装文档的链接；产物名、端口、环境变量一改，六份一起改。仓库里的 `AGENTS.md` 还把发版和更新日志列为两条红线：推 tag 之前要人确认，日志要逐条过目。

## 先回答一个问题，再决定装不装

装之前只需要想清一件事：这台网关是给自己用，还是要分享给网络。

自己用，桌面端最省事——装完、加账号、建 Key、把客户端指到 `127.0.0.1:3065/v1`，然后用一个真实小任务走一遍（改一个函数，或者查清一份日志里的报错），核对报表里的成功率和 Token 和客户端显示对不对得上。对不上就先别接入正式工作流。

要分享，先把三件事定下来：Key 怎么分权、面板留在哪个网段、上游账号被谁用。这三件定不下来，后面出的问题不是配置问题。
