你在排查服务器问题的时候，大概率遇到过这种时刻：端口被占了、CPU 被某进程吃满了、一个文件被锁住了，你 `ps` 一看，PID 有了，但也只是有了。它从哪来的、是谁把它拉起来的、为什么它死了还会复活——你得自己去 `lsof`、`ss`、`systemctl`、`docker ps` 一堆命令里翻来翻去。

witr 就是冲着这个痛点来的。它打出的口号特别直白：

> Why is this running?（这东西为什么在跑？）

## 是什么

witr 是一个命令行工具，用 Go 写的，Apache-2.0 协议开源，发布不到一年，GitHub 上已经有 2.3 万星。

它的核心思路很简单：无论你查的是一台机器上的进程、一个端口、一个容器还是一个被锁住的文件，最终都能落回一个 **PID**。而 witr 就沿着这个 PID，把"它怎么启动的、是什么让它在跑、它属于哪个上下文"这一整条因果链给你查出来，一次性摊开。

区别在于：`ps`、`top`、`lsof`、`docker ps` 这些老工具告诉你**什么在跑**；witr 告诉你**它为什么在跑**。

官方 README 给的定位很准：老工具把状态和元数据摆出来，但"为什么"要你自己跨工具去脑补。witr 把因果关系变成显式的东西。

## 查到的是什么样的答案

看一个真实感很强的例子。`witr node`，一个 node 进程为什么在跑？它的报告长这样（摘自官方 README 的示例输出）：

```
Target      : node
Process     : node (pid 14233)
User        : deploy
Command     : node /srv/expense-manager/index.js
Started     : 2 days ago
Restarts    : 3

Why It Exists :
  systemd (pid 1) → PM2 v5.3.1: God (pid 5034) → node (pid 14233)

Source      : pm2-deploy.service (systemd)
Unit File   : /etc/systemd/system/pm2-deploy.service
```

关键就是那行 **Why It Exists**——一条从 `systemd` 到 `PM2` 再到 `node` 的完整起父链。它不是猜的，是顺着 PID、PPID、systemd service、容器 runtime 一路追踪出来的。

查端口一样清楚。`witr --port 5000` 会告诉你这个端口被哪个进程占着、这个进程又是被谁拉起来的。查容器，`witr --container api` 会跨 Docker、Podman、Kubernetes 等一堆 runtime，连带镜像、Compose 项目和发布端口一起给你。

## 常用命令速查

witr 的命令设计很对称，好记：

- `witr`：直接进交互式 TUI（鼠标可点，四个标签页翻看进程、端口、容器、文件锁）。
- `witr node`：按进程名查，默认模糊匹配（`node` 会命中 node、nodejs 等）；加 `--exact` 精确匹配。
- `witr --port 8080`：查 8080 端口被谁占用、为什么。
- `witr --pid 1234 --tree`：查某个 PID 的祖先进程链，用树形展示。
- `witr --container api`：查容器（跨各种 runtime）。
- `witr --file /var/lib/dpkg/lock`：查哪个进程锁着这个文件。
- `witr --port 5432 --pid 8123`：多个目标可以混着同时查，按你输入的顺序逐个出报告。
- `witr --port 8080 --json`：输出成 JSON，给脚本和 AI agent 用。
- 加 `--short` 只显示祖先链、`--tree` 显示成树、`--warnings` 只看警告、`--verbose` 补充内存和 IO 明细。

## 专门给 AI 编程助手留了接口

这是 witr 眼里一个很有想法的场景：AI 编程 agent（Claude Code、Codex、Cursor 这些）在干活时经常撞上"端口被占""有僵进程""容器搞不清"的情况，以前只能自己一串 `lsof`、`ps`、`netstat`、`docker ps` 去拼。

witr 让一个命令就能回答——专门为 agent 设计了两点：

- **`--json`**：整份报告（进程、祖先链、来源、警告）输出成结构化 JSON，失败时是 `{Target, Error}`，agent 不用解析文字。
- **退出码**：`0` 找到了没警告；`1` 找到了但有警告（这不代表失败）；`2` 没找到；`3` 权限不足（用 sudo 重试）；`4` 参数或匹配有问题；`5` 内部错误；`6` 找到了但查不清是谁拉起的。

它还直接提供官方 agent skill，Claude Code 里 `/plugin marketplace add pranshuparmar/witr` 就能装上，教 agent 该用哪条命令、怎么读 JSON 和退出码。



## 适合谁

- **普通运维/后端开发者**：端口冲突、进程查不清楚、写 systemd 服务排查——一个 `witr --port 8080` 比来回倒三个工具快得多。
- **做测试的你**：定位偶发失败非常有用。接口被占用、文件被锁、环境里莫名多出的进程，以前要一步步猜，现在一条命令能看到"谁起的、为什么还活着"，很适合写进故障复现的步骤里。而且退出码、`--json` 输出都能直接进脚本做断言。
- **用 AI 编程助手的团队**：把 `witr --port <PORT> --json` 这类话术写进 `AGENTS.md`，agent 撞到端口冲突时就不用绕圈了。

## 它做对了什么

很多命令行工具停在"把信息读出来"。witr 多做了一层——把**因果**读出来。这听着简单，实际上是在进程模型、systemd、容器 runtime、文件锁这些本来各自为政的系统之间，硬搭了一座桥，还要跨那么多平台保持一致。

这正是旧工具集体缺席、而开发者和 AI agent 都需要的那块拼图。如果你想亲手验证，项目还提供在浏览器里直接试玩的模拟环境，不用安装就能先跑一遍
