说实话，回头看 1 月这堆事，我第一个反应不是“我干了不少”，而是：

30天、一个普通工程狗、把提示词调教、封面自动化、发版巡检、代理折腾、身体恢复、歌单整理，全塞进同一份月度清单里，结果居然还都“done”了。

说白了就是：我在用一堆新玩意儿把工作流程重新装了一遍，然后不停地回滚、修补、再试。

把一堆“看起来很酷”的工具和流程，真拿来用之后到底会发生什么。因为 AI、Agent、自动化这些东西突然就挤到日常里，谁都绕不开。真正想劝的是别被“完美流程”绑死，要能随时切换方案，才能活下来。

### article-prompt

说是 done，其实更像是——**暂时没力气再改了**。

prompt 用 skill 的方式重写了 N 轮，这个过程一点都不优雅，说白了就是反复试、反复翻车、再反复精修。

一开始还挺自信，结果一进深水区就发现自己像揉面：规则要一条条揉进去，太干了不行，太湿了也不行，得“==精打细磨==”。后来我才意识到，真正难的不是“写 prompt”，

而是**学会怎么跟 AI 说人话**。

每一条规则，不是写上去就完事，而是要磨，磨到模型真的理解你在要什么。

过程真的就是一撮再撮。我当时没绷住，觉得自己像在厨房反复补盐。

狗东西，真费劲。

这块我当时其实有点绕，后来干脆拉了个表，不然自己都快把自己说晕了。

| **当时以为的事**  | **实际踩下来的感受**           | **现在的判断**               |
| ----------------- | ------------------------------ | ---------------------------- |
| prompt 写清楚就行 | 不反复打磨，模型理解永远偏     | prompt 本身就是个长期工程    |
| skill 只是形式    | skill 会强烈影响模型执行稳定性 | skill 是“行为约束”，不是装饰 |
| 多规则=更聪明     | 规则写不好反而更蠢             | 少而准，比多而杂重要         |

### 封面图制作及上传自动化

我之前看到有人用 prompt 直接生成 HTML 卡片，说实话当时有点被震到——这思路太骚了。后来自己拆流程，其实就是：描述风格 → 图文分离 → 生成 HTML → playwright 截图 → 推送上传。

听起来顺，但真做的时候才发现，描述一旦含糊，生成结果就会非常“自由发挥”。流程像拍证件照：先化妆、再摆姿势、最后机器咔嚓。一步错就像证件照把你头砍掉不过一旦跑顺了，**那种点一下就出封面的爽感，是真的会上头**。

![image-20260201133556527](https://cdn.jsdelivr.net/gh/xsoway/xsoway_pic_db@master/image-20260201133556527-9924162.png)

**封面自动化步骤**

1. 明确你想要的封面风格（我当时用“卡片式”）
2. 把文字内容和图片素材拆开，别糊一起
3. 用 prompt 生成 HTML 结构
4. 把 HTML 渲染成浏览器页面
5. 用 playright 进行截图
6. 把截图产物推送上传
7. 做一次肉眼复查（不然翻车更快）

### 电报数据抓取

这段时间对几个电报账号的内容抓取流程做了一轮优化。

整体链路现在比较清晰：

**定期抓取 → 保存至 Excel → 挑选内容 → 优化修改 → MD → push**

没有引入太复杂的东西，更多是在稳定性和可用性上做微调。抓取频率、数据结构、筛选逻辑都顺了一点，后续人工介入的成本也明显低了。

目前跑起来还算稳定，数据可控，可复用性也在预期范围内。

不是那种“眼前一亮”的优化，但属于**能长期用、不容易出问题**的那一类。

![image-20260201133710104](https://cdn.jsdelivr.net/gh/xsoway/xsoway_pic_db@master/image-20260201133710104-9924235.png)

一切还算 **that’s ok**。

先这样跑着，等真实使用再看要不要继续拆细或自动化更多步骤。

### 发版质量检测平台开发

发版检测这一块，是 1 月里让我纠结最久的地方。

一开始我是真的想把脚本直接塞进生产服务器，进 pipeline 强制执行。结果现实直接给我浇冷水：服务器系统太老，依赖装不上；巡检还要调大模型，慢得离谱，真卡在 pipeline 里，发一次版能把人逼疯。

![image-20260201134127006](https://cdn.jsdelivr.net/gh/xsoway/xsoway_pic_db@master/image-20260201134127006-9924489.png)

这地方我是真纠结过一阵子，后来也是靠写表把自己劝明白的。

| **方案**        | **当时纠结点**     | **真正放弃的原因**   |
| --------------- | ------------------ | -------------------- |
| 强绑定 pipeline | 看起来“规范”“高级” | 会拖慢发版，风险放大 |
| 上生产服务器跑  | 操作统一           | 系统太旧，依赖地狱   |
| 本地拉代码巡检  | 一开始觉得不够正规 | 实际最灵活、最可控   |

后来反倒想明白了：**现在还是实验阶段，没必要跟流程死磕**。

索性写了个前端页面，发版前拿 git 地址，本地拉代码巡检，生成报告当参考。巡检独立了，不和发版冲突，还能随时调策略。回头看，这种“退一步”的方案，反而更工程化。这就像体检：你可以去医院排队（pipeline），也可以自己先在家量个体温（本地巡检）。我当时还觉得自己挺聪明，后来再看，这其实是绕开僵硬流程的自救。

### antigravity

antigravity 的登录问题我已经放弃挣扎了。**但又登上了!!!**

这个东西真的需要运气和玄学，我最后直接放弃了：使用 TUN 方式无解、换代理工具无解、换账号/换区域也无解。它像抽奖机，投币无数，连个灯都不亮。我当时判断错了，以为“换个姿势就能登上”，结果现实直接扇脸。

我现在也不确定是不是我运气差，还是这玩意儿本来就这样。

| 尝试            | 结果                  |
| --------------- | --------------------- |
| 使用 TUN 方式   | 无解                  |
| 换代理工具      | 无解                  |
| 换账号 / 换区域 | 无解                  |
| n天后再次尝试   | ==嘿,别说,还真别说!== |
