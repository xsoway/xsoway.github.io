想用 AI 画一张手绘风格的图，卡住的往往不是"画什么"，而是"怎么把想要的那种画风说清楚"。

要吉卜力那种柔和水彩、暖光的调子，还是要小豆人黑色涂鸦讲解图的利落，还是水墨那种"墨分五色"的写意——对着生图模型各写各的提示词，每个人写出来都不一样，翻来覆去调，最后效果还不稳定。

GitHub 上这个 2.4k star 的仓库 `threerocks/hand-drawn-styles`，把这件事做成了工程：一套工具无关的手绘画风提示词配方库，内置 21 套已验证画风，说一句"用吉卜力风画一只下雨天打伞的猫"，它就能给出可以直接复制的完整生图提示词。

## 同类产品横向对比

先横向看几个常见的生图方式，都是日常能接触到的：

| 方式 | 要不要花钱 | 在哪用 | 主要帮什么 | 画风稳定吗 | 点评 |
|---|---|---|---|---|---|
| 直接用 AI 生图，自己敲提示词（即梦/Midjourney/gpt-image） | 订阅或按量付费 | 对应模型 App/网页 | 想画啥画啥 | 看个人，全凭手感 | 自由，但每次都要从零磨词，风格漂移看运气 |
| 网上找别人分享的提示词模板，复制粘贴 | 免费 | 各平台/文档 | 抄一段现成的 | 中等，好坏看来源 | 省事，但散、不成体系，改一个就得整个重搜 |
| 商业儿童绘本/插画生成产品 | 订阅制偏多 | 对应产品 App | 一键出成品绘本 | 产品内较稳 | 门槛最低，但画风锁死在它家，想换风格出不来 |
| 本文这个仓库 `hand-drawn-styles` | 免费，MIT 协议 | 接入 Claude Code / Codex / Cursor 等 Agent 工具 | 一套配方管 21 种画风，出稳定 prompt | 高，锚点 + 验收兜底 | 不替模型生图，专治"风格说不清、调不稳定" |

评测结论：前面三种，本质都是在跟"风格描述"这件事较劲——要么自己练，要么依赖散装模板，要么被产品锁死。这个仓库选择不动手画，而是把手绘风格本身做成一套可复用、可替换、可验收的配方，让任何 Agent 工具都能稳定吐出合格的提示词。

## 它是什么

一套**工具无关的手绘画风提示词配方库**，或者说，一个装进 AI Agent 里的"手绘风格能量包"。它不是生图工具本身，也不强制绑定某家模型；它只负责一件事——把你要画的内容，套进内置的某一套画风配方，产出可以直接交给图像模型使用的最终提示词。

- **定位**：画风配方库，不是生图器，也不是模板网站。
- **协议**：MIT 开源，代码随意改随意用。
- **内容**：内置 20 种整数编号画风 + 稳定变体 3.1，共 21 套配方。从 xkcd 火柴人、蜡笔童涂、吉卜力、水墨写意，到复古像素、北欧纸雕、3D 潮玩软偶，分八大组：拟真手绘、线条讲解速写、故意画烂、传统复古质感、动画概念设定、纸艺立体手工、绘本扁平北欧、3D 潮玩。
- **语言**：配方中英混合，有中文名，也有英文别名（`ghibli`、`ink-wash`、`pixel-art` 这样），说中文名、编号（"用 3 号画风"）或英文别名都能触发。
- **是成品，不是模板**：下载一个轻量包装进 Agent 就能用，不用自己拼装。

GitHub 页面上看到的星数是 2.4k，分叉 258，提交 45 次，主要语言 Python，作者是 threerocks（文件署名 liulei）。


## 项目结构

这段偏技术，看不懂可以跳过，不影响理解主体内容。想看它内部怎么组织，接着往下。

仓库不大，600K 出头，核心只有协议、配方、渲染器三样，外加配套的检查与打包脚本。目录树直接来自仓库根目录：

```
hand-drawn-styles/
├── README.md            # 总览与用法
├── LICENSE              # MIT
├── PROTOCOL.md          # 核心协议：选风格 / 比例 / 占位符 / 输出（工具无关）
├── STYLES.md            # 核心配方：20 种整数编号画风 + 3.1 变体（工具无关）
├── SKILL.md             # Claude Code 适配层（薄，指向上面两个文件）
├── AGENTS.md            # Codex / Gemini / Cursor 等适配层（薄）
├── INSTALL.md           # 轻量包的安装与检查说明
├── assets/              # 图片地址与校验清单、隐私审计记录
├── docs/                # 图片托管与维护规则
├── scripts/             # 渲染器、安装检查、打包与回归测试
├── examples/            # 公开样图链接与输入示例
└── benchmarks/          # 研发对照图与验收记录，不进默认安装包
```

按"谁在发号施令、谁执行、靠什么落地"分层看，是这样：

| 层 | 核心文件 | 管什么 | 谁调用 |
|---|---|---|---|
| 入口/适配 | `SKILL.md`、`AGENTS.md`、`README.md` | 让各类 Agent 工具识别并触发画风能力 | Claude Code / Codex / Cursor 等 |
| 规则核心 | `PROTOCOL.md`、`STYLES.md` | 5 步执行流程、21 套画风配方（工具无关） | 入口层指向，渲染器读取 |
| 执行端 | `scripts/render_prompt.py` | 从配方原样提取并填充占位符，产出 prompt | Agent 调用 |
| 质量保障 | `check_skill.py`、`validate_style_20_asset.py`、3 个回归测试 | 安装检查、成图验收、全画风回归 | 装好后 / 正式生产时 |
| 持久存储 | `assets/image-manifest.json` + Netlify | 参考图地址与 SHA-256 清单；图片不进 Git | 渲染器按需下载 |

README 里关于目录的说明原话如此："核心是工具无关的 `PROTOCOL.md`（执行流程）+ `STYLES.md`（画风配方），`SKILL.md`、`AGENTS.md` 是薄适配层（薄，指向上面两个文件）"。这套"规则核心只放一份、各工具只做薄入口"的思路，是它能横跨多种 Agent 通用的关键——配方只维护一处，不会每家改一份、各写各的。

## 做什么用的

解决的核心烦恼：**让"描述画风"这件事变得可复用、可稳定、不漂移**。

平时用 AI 生图，风格是藏在提示词文字里的玄学——同一个词，今天这么描述效果好，明天换一种说法又偏了。这个仓库把这一步收敛成固定配方：

- 想画什么，只用说内容；画风是哪一套，由编号或名字指定。
- 配方是写死的：线条粗细、色彩规则、留白、纸感、硬性负向约束（比如"严禁均匀灰度滤镜""严禁照片写实"），都在模板里，Agent 不自由发挥。
- 4 个需参考图片锚点的画风（3.1、13、19、20）还带"验收合同"，输出不合格直接拒掉重画，不留模棱两可的中间态。

仓库的维护说明里理得很清楚：核心是工具无关的 `PROTOCOL.md`（执行流程）加 `STYLES.md`（画风配方），`SKILL.md`、`AGENTS.md` 都是薄适配层，只负责指路，不重复内容。这套结构让同一个配方在 Claude Code、Cursor、Codex CLI、Gemini CLI、Cline、Windsurf 里通用。

## 怎么用

安装这一步，直接把下面这句话发给 Agent 工具就行：

```
帮我安装这个 Skill 的轻量包：https://github.com/threerocks/hand-drawn-styles/releases/latest/download/hand-drawn-skill.zip
解压后保留 hand-drawn/ 的完整目录结构，并运行 scripts/check_skill.py 验证安装。
```

装好之后，在支持的 Agent 工具里直接说：

- "用吉卜力风画一只下雨天打伞的猫"——指定画风，直接出提示词。
- "用手绘风画一只在下雨天打伞的猫"——没指定画风，Agent 会先列菜单让你选，回复编号就行。
- "用 8 号画风画……"——按编号调用也行。

出图比例是可选参数：你不传，纯风格画风不注入任何比例；传了，按你的来。像 xkcd 火柴人、小豆人这类版式画风，只注入"多格网格"这种软结构提示，不写死数字。

跑一下它自带的渲染器，能直接用命令看到一套配方实际输出什么：

```bash
python3 scripts/render_prompt.py --style minimal-line --var 'N=3' \
  --var '分镜列表=第一格：设置计时器。第二格：专注工作。第三格：休息。'
```

输出的就是一份完整的 xkcd 火柴人画风提示词，里面相当细致：细线描边、圆角分镜、每格手写中文小标题，最后还有一条硬性负向约束"严禁实心黑色填充、严禁剪影、严禁排线与阴影"。

## 画风稳定的三道保险：把"稳定"做成检查点

配方库、提示词模板这类东西网上不少。这个仓库真正让人停一下的，是它给"画风稳定"这件事上了三道工程检查——这也是跟其他同类 prompt 库不一样的地方。

**第一道：用锚点和像素哈希锁定画风身份。**

画风 3.1（蜡笔童涂-潦草自画版）、19（圆头红线极简童画）、20（暖黄墨线情绪小剧场）在正式生产时必须携带一张画风参考图作为锚点。这张锚点图按 PNG 尺寸和解码后的像素级 SHA-256 校验——不只是"图片对得上"，是从像素层面锁死"必须是这张原图"。源码里的 `validate_style_19_anchor`、`png_pixel_sha256` 就是这么干的。

也就是说，画风身份不是一个可以随便换的颜色方案，而是一个有严格校验指纹的资产。锚点缺失、损坏、被换图，或者调用端传不了参考图，就**失败关闭**：停止正式生产，明确报告"画风锚点未生效"，绝不退而求其次输出一个没锚点的简化版蒙混。

实测了一下，不带锚点直接调 3.1 的渲染器，报错是：

```
render_prompt: 图片下载失败: assets/style-3.1/anchor-family.png;请检查网络后重试 hosted_images.py fetch
```

拒绝懒散降级，宁可报错也不给凑合的结果。这在生图这个普遍"差不多就行"的领域里，是很硬的态度。

**第二道：成图要过"验收合同"。**

光有锚点还不够，成图质量也要设门槛。画风 19 的输出带一份 `acceptance_contract`：调用端必须按 7 项维度给候选图打分，总分至少 30/35、且没有任何硬失败项，才能标为 final；不及格整张拒收，不能靠统一加粗描边、加滤镜补救。

画风 20 更彻底，用机读验证器 `validate_style_20_asset.py` 自动检查：暖白、黑色、芥末黄、珊瑚红这些颜色占比对不对，禁用冷色和荧光黄有没有超量；评分卡要绑定候选图的 SHA-256，并确认主体数量、物种、身份、必要物件都没被模型偷换。只有总分至少 34/40、无硬失败项、验证器退出码为 0，才放行。

落到手上，是一份**可机读的成图验收标准**：人眼之外多了个程序在把关"画得对不对"。

**第三道：三阶段工作流，把"最后那一笔"也写进流程。**

画风 3.1 的正式生产不是一次搞定，而是强制三步：基础生成 → `scribble-correction`（第一次涂抹修正）→ `scribble-chaos-correction`（打散残余的规整排线，让涂鸦更像孩子随手画的）。前两阶段的输出只能算中间图，只有第三阶段才算 final，任何一步缺了都不能继续。

概括起来：这就是把"AI 画的图不够糙、太规整"这类常见缺陷，拆成了两个可单独修正的阶段，而不是寄希望于一次提示词就全对。它把"凭感觉修"改成了"按流程修"。

## 它的过程记录：稳定不是空口

这套"验收"不是写个口号，仓库里有实打实的过程记录。

`benchmarks/` 目录下存了一份 2026-07-13 的 MJ 标杆对照实验：为了让 gpt-image（codex 出图）摆脱"数字感偏重"，作者拿 Midjourney V7 当材质标杆，把 4 个画风做成对照——MJ V7 原图当标杆，仓库原配方当基线，再叠加一层"实拍纸质感增强层"当改进版，逐张对比。

结论表记的是准确差距：3.1 号基线的问题是"干净数字蜡笔、纸面过平"，叠层后"纸纹/运笔方向/蜡质/折痕齐备，≈MJ"；水墨是"纸不够实拍、填色偏满"，叠层后"皱纸摄影感到位"；还有一处承认 MJ 全程无视"低饱和/留白"这类纪律约束，反而是叙事与配色纪律是 gpt-image 的强项。

这种把"AI 出图数字感重"做成有基线、有对照、有结论的对照实验，本身就是测试思维。仓库里还带了 67 个回归测试（渲染器 47、图片托管 12、安装 8），`check_skill.py` 安装检查覆盖全部画风调用。

## 边界与代价

工程化不是万能的，这套系统也有它的前提和让渡：

- **它只出 prompt 或调用包，不生图**。要得到最终图片，还是得自己接图像模型（gpt-image、即梦、Midjourney 都行）。它是提示词这道工序的标准化，不是端到端着色的替代。
- **正式的画风（3.1/19/20）对调用端有硬要求**：得能传参考图、能跑验收流程。普通纯文本对话只能拿到预览，拿不到正式生产包。
- **全流程严格是双刃剑**：先把流程复杂，换来的是稳定和可回滚；如果只是想随手画一张玩，纯文本配方图个快就够了，不必每次都走完整验收。
- **图片不放进仓库**：靠 Netlify 公开托管、清单登记地址和哈希，安装包控制在 1 MiB 内。这带来下载依赖网络，首次调用要联网。

## 一个小结

这个仓库给到的启发不大不小：生图提示词这种常被当成"玄学手感"的东西，是可以被工程化、被验收、被复现的。锚点锁定身份、验收合同卡成图标准、三阶段工作流补最后的糙劲——每一环都在回答一个问题：怎么证明这次出的图，就是用户要的那种风格，而不是模型临时发挥的"有点像"。

对于平时做测试、跟验收标准打交道的人来说，这套思路不陌生：先把"合格"定义成可机器判定的规则，再让程序来兜底。把这套思路搬进其他 AI 输出不稳定的场景，比如 Agent 生成的代码、报告、文案，一样成立——先别急着说"模型发挥不稳定"，先看看验收规则定清楚了没有。
