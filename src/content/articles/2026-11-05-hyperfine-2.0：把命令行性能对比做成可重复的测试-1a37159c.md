# hyperfine 2.0：把命令行性能对比做成可重复的测试

一段 Python 脚本优化后，运行时间从多少降到了多少？换了一种搜索工具，究竟快了多少？在终端里用 `time` 测一次，能得到一个数字，却很难据此判断改动是否有效：文件缓存可能变了，机器可能正在运行其他任务，第一次启动和后续运行也可能有明显差异。

[hyperfine](https://github.com/sharkdp/hyperfine) 是一个开源命令行基准测试工具。它可以重复执行指定命令、统计耗时、安排预热和准备动作，并把结果导出供后续比较。对于经常跑脚本、测试工具或构建命令的人，它能省掉手工循环执行、抄录时间和计算平均值的工作。

2026 年 10 月 7 日发布的 **hyperfine 2.0.0** 还加入了更多性能指标，同时调整了命令执行方式和报告格式。本文以官方仓库和 v2.0.0 发布说明为依据，所有命令均为用法示例，不代表在特定机器上完成了实测。

## 从一条命令开始

macOS 可以通过 Homebrew 安装，Ubuntu 和 Debian 可使用系统包管理器：

```bash
# macOS
brew install hyperfine

# Ubuntu / Debian
sudo apt install hyperfine

# 查看实际安装的版本
hyperfine --version
```

系统仓库提供的版本可能落后于 GitHub 发布版。下文涉及 `--metrics` 和新版 JSON 结构的命令，按 **2.0.0** 编写；运行前应确认版本。

最基本的用法只需给出待测命令：

```bash
hyperfine 'python3 script.py'
```

hyperfine 会多次运行命令并给出统计摘要。默认至少运行 10 次，并估算运行次数，使测试累计达到约 3 秒；也可以固定次数：

```bash
hyperfine --runs 20 'python3 script.py'
```

要比较两个实现，可以把两个命令放在一起：

```bash
hyperfine --warmup 3 --runs 20 \
  'python3 parser_old.py' \
  'python3 parser_new.py'
```

这里的 `--warmup 3` 表示先预热 3 次，预热结果不计入正式统计。`--runs 20` 表示正式测量 20 次。**两份脚本应处理相同输入、产生等价结果**，否则“更快”可能只是因为少做了工作。

## 为什么不能只跑一次

基准测试测的是指定条件下的执行表现。即使同一段程序，结果也会受到 CPU 负载、磁盘缓存、进程启动、输入大小和后台任务的影响。多次运行至少能够观察执行时间是否稳定，而不必把某一次偶然的最快结果当成结论。

读结果时，重点关注平均耗时、标准差以及极值。平均耗时反映这组样本的总体水平，标准差描述波动程度；如果两组结果差异很小、波动却很大，就不宜直接宣称某个版本更快。hyperfine 也会提示可能的异常值，但**检测到异常值不等于自动排除了所有干扰**。

预热同样不是越多越好。它适用于希望比较“缓存已经建立后的运行表现”的场景。如果业务实际关注首次启动或冷缓存读取，那么反复预热会改变问题本身。先决定测量对象，再选择测试条件。

## 让每轮测试从可比较的状态开始

假设某个脚本会把结果写入缓存文件。第一轮创建文件，后续轮次直接读取，测出来的便不是同一种工作量。这时可以通过 `--prepare` 在每次正式执行之前整理环境：

```bash
hyperfine --runs 20 \
  --prepare 'rm -f /tmp/bench-demo.cache' \
  'python3 build_cache.py'
```

这个示例假设脚本使用 `/tmp/bench-demo.cache`，只应对**专门准备的测试文件**执行删除操作。`--prepare` 的时间不包含在待测命令耗时里。不同程序可能需要重置数据库、清除测试产物或恢复相同的数据集，但这些操作应尽量隔离，不能误清理真实业务数据。

常用的执行阶段可以这样区分：

| 参数 | 什么时候执行 | 典型用途 |
| --- | --- | --- |
| `--setup` | 每组基准测试开始前一次 | 编译该组对应的程序 |
| `--warmup` | 正式采样前 | 观察热缓存状态下的性能 |
| `--prepare` | 每次测量前 | 恢复输入或清除测试产物 |
| `--conclude` | 每次测量后 | 做单轮结束处理 |
| `--cleanup` | 每组基准测试结束后 | 清理临时构建结果 |

`--prepare` 等命令自身通过 shell 执行；这点与 2.0 默认直接执行待测命令的行为不同。

## 2.0 有两个变化，旧脚本需要留意

### 1. 默认不再经过中间 Shell

在 1.x 的典型用法中，命令可以依赖 shell 展开。**2.0 默认直接启动待测程序**，避免额外 shell 启动及其耗时修正带来的干扰。但管道、重定向、通配符和环境变量展开不再自动生效。

例如，下面的命令需要明确启用 shell：

```bash
hyperfine -S 'grep TODO src/*.py > /dev/null'
```

`-S` 相当于 `--shell=default`。如果待测对象只是一个可执行程序和固定参数，通常不必添加它：

```bash
hyperfine 'python3 script.py'
```

这对几毫秒以内的短命令尤其有意义：测量越短，启动包装层引入的噪声越容易影响结论。迁移已有脚本时，应检查是否使用了 `|`、`&&`、`>`、`*`、`~` 或 `$变量` 等语法。

### 2. JSON 报告的字段位置发生了变化

2.0 的 JSON 格式升级为 **schema version 2**。旧版脚本读取的 `results[i].mean`，在新版中应改为读取 `results[i].summary.time_wall_clock.mean`；每次运行的耗时则可从 `measurements` 中读取。

```bash
hyperfine --runs 20 \
  --export-json benchmark.json \
  'python3 script.py'
```

下面是一个适用于 2.0 JSON 结构的 Python 读取示例：

```python
import json

with open("benchmark.json", encoding="utf-8") as f:
    report = json.load(f)

assert report["schema_version"] == 2, "需要 hyperfine 2.x 格式的报告"

for result in report["results"]:
    stats = result["summary"]["time_wall_clock"]
    print(result["command"], stats["mean"], stats["stddev"])
```

这段代码只展示字段读取方式，并不是完整的性能回归判定器。报告中可以保留每轮测量、软件版本和平台信息；如果已有 CI 流程读取旧版 JSON，升级时应同步修改解析脚本，并用两份不同版本的样本文件进行兼容性测试。

此外，2.0 移除了 `--time-unit`、`--sort`、`--reference` 等选项，原有调用需要按发布说明调整。

## 从耗时扩展到内存和 CPU 指标

只看完成时间，有时无法解释优化是否带来了其他代价。2.0 增加了 `--metrics`，可以选择墙钟时间（从开始到结束的实际经过时间）、CPU 时间、峰值常驻内存，以及受操作系统与硬件支持情况限制的 CPU 指令数、缓存未命中等指标。

```bash
hyperfine \
  --metrics time_wall_clock:ms,memory_peak_resident:MiB \
  'python3 script.py'
```

官方文档说明，2.0 默认展示墙钟时间和峰值常驻内存，但 Windows 暂不支持该内存指标。峰值 RSS 也不等同于整个进程树在同一时刻的内存总和；CPU 硬件计数器的统计范围和可用性会随平台不同而变化。因此跨平台比较时，必须先核对指标的测量范围，不能只比较数值。

想观察不同参数的影响，可以使用参数扫描：

```bash
hyperfine -P workers 1 8 \
  'python3 worker_demo.py --workers {workers}'
```

这里会生成 1 到 8 的参数组合并逐一测量，适合探索本地处理线程数、批量大小等因素。如果参数改变了输入规模，比较结果时还需要同时考虑完成的工作量；不能把“处理更多数据所用时间更长”直接判定为性能退化。

## 放进测试工作流，应该怎么用

对于测试开发，hyperfine 更适合做**本地程序、测试工具和批处理任务的性能基线**，例如：

- 对比同一份测试数据在两版 JSON 解析器中的执行时间。
- 检查用例生成脚本、测试报告生成器或日志分析脚本修改后的耗时和内存变化。
- 对比不同参数下的批处理工具，找到稳定的配置区间。
- 将版本、输入数据、执行参数和导出的 JSON 一并归档，供后续回归分析。

一个可落地的最小流程是：固定输入数据与依赖版本 → 确认新旧程序输出等价 → 在相同机器环境下预热、重复运行 → 导出 JSON → 检查均值与波动 → 对明显退化的结果复测并定位原因。

如果准备把它接入 Jenkins 或 GitHub Actions，建议先把结果作为**趋势报告**，不要第一天就根据一次均值变化自动判定构建失败。共享 CI 机器负载变化较大，容易出现误报。需要自动阻断时，应先积累稳定样本，再定义适合项目的阈值、允许波动和复测规则。这个工作流属于工程建议，并非本文已完成的集成验证。

也要分清它与 Locust、JMeter 这类压测工具的职责。hyperfine 重复运行的是命令，主要观察单次任务的资源消耗和执行耗时；它不直接生成并发用户、请求到达率或服务端吞吐量曲线。即便被测命令是一次 HTTP 请求，也不能仅凭 hyperfine 的运行次数推断服务的并发性能或容量上限。

## 使用时留意三个容易忽略的问题

**命令启动开销算不算测试内容？** 如果测的是完整 CLI 用户体验，程序启动就是成本的一部分；如果只关心一个 Python 函数的执行速度，反复启动解释器会掩盖函数本身的差异。这种情况应考虑在程序内部使用更细粒度的基准测试，而不是勉强用外部命令计时。

**测试顺序是否影响结果？** 两个命令按顺序测量时，机器温度、系统负载和缓存状态可能发生变化。对于差异很小的方案，建议改变对比顺序、在多个时段复测，并保留机器与软件环境信息。

**速度提升是否损害正确性？** hyperfine 负责测量，不负责验证两个程序产生的结果是否一致。正确性检查应放在基准测试前，测试输出和输入数据也应单独管理。

## 什么时候可以开始用

如果手头经常有“优化前后快了多少”的问题，hyperfine 可以直接承担重复运行、统计和导出报告的工作。它不要求先搭一套性能测试平台，用一条命令就可以建立最初的对照。

对于长期维护的测试工程，更合适的用法是把基准测试命令、固定数据和环境信息放进仓库，让同事能够复测。性能数字只有对应明确的测试条件，才具备讨论和比较的基础。
